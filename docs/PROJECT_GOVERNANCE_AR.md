> هذا ملخص حوكمة وليس إعلان جاهزية إنتاجية. سجلات Stage وملفات الاستمرارية ونتائج CI هي الأدلة التفصيلية التي يجب مراجعتها قبل أي ترحيل أو نشر.

## 1. دور ERP داخل المنظومة الأوسع

ERP Global Pro منتج مستقل لإدارة المؤسسات، متعدد الشركات، مستهدف للقطاعات المختلفة عبر حزم قطاعية. استقلاله مطلب أمني وتشغيلي، لأن بياناته تتضمن السجلات المالية والمخزون والموظفين والعملاء.

- يبقى المستودع وقاعدة البيانات والنشر والأسرار والنسخ الاحتياطية مستقلة عن AI Chat App وLumen.
- لا تتشارك الشركات المستأجرة البيانات التشغيلية؛ هوية المستخدم عامة لكن الصلاحيات تأتي من عضوية نشطة داخل الشركة.
- يمكن مستقبلاً استهلاك AI Core عبر API لمساعدة المستخدمين في التقارير أو التحليل، دون أن تمنح النواة صلاحية مباشرة لإصدار قيود محاسبية أو تعديل المخزون أو الرواتب.
- فشل AI Core أو أي تطبيق آخر لا يجوز أن يوقف وظائف ERP الأساسية.

## 2. التقنية والقرارات الأساسية

- التطبيق الحالي: Flask + SQLite v8 وواجهة JavaScript خالصة.
- اتجاه قاعدة البيانات النهائي المعتمد: PostgreSQL بوصفها مصدر الحقيقة بعد ترحيل كامل ومتحقق، لا عبر dual-write.
- اتجاه تعدد الشركات: هوية عالمية للمستخدم، وعضويات وأدوار مرتبطة بالشركة، و`company_id` إلزامي لبيانات كل شركة، ومفاتيح أجنبية مركبة وRLS بعد اكتمال التطبيق والاختبارات.
- محول Psycopg 3 والنماذج الحالية مراحل تمهيدية؛ لا تعني أن التطبيق أصبح متصلاً بـPostgreSQL.
- الأرشيف الأصلي محفوظ دون تعديل، ويجب الاحتفاظ به وبـSHA-256 الأصلي المسجل في وثائق المشروع.

## 3. الوضع الذي تم التحقق منه

- رأس `main`: `6badac066a0fdd10ae6bda79f753fee5edae6210`.
- طلب #1 على الفرع `stage25/application-tenant-context-plan` ما زال Draft ومفتوحاً.
- فحوص CI لرأس PR #1: **4/4 ناجحة** (Backend Python 3.11، Backend Python 3.12، واختبارات PostgreSQL الحية على النسختين).
- وفق وصف PR، نجحت 30 اختبار PostgreSQL حي على PostgreSQL 16 في Python 3.11 و3.12، و314 اختبار Backend لكل نسخة، و11 اختبار HTTP حقيقي لكل نسخة، إضافة إلى 11 اختبار preflight مركّزة لكل نسخة.
- نتائج هذه الاختبارات تعتمد على بيانات اصطناعية ضمن CI. لم يُنفّذ بعد preflight على نسخة قاعدة بيانات حقيقية مستعادة وغير متصلة بالتشغيل.
- SQLite v8 ما زالت قاعدة التطبيق الفعلية.
- `TENANT_DATA_SCOPING_ENABLED=False` ويجب أن تبقى كذلك حتى إغلاق بوابة الإطلاق متعددة الشركات.
- لا يوجد في الأدلة التي تمت مراجعتها cutover إنتاجي إلى PostgreSQL أو نشر إنتاجي معتمد.

## 4. الأولوية التنفيذية التالية — Stage 25C

1. الحصول على نسخة SQLite v8 مستعادة ومتحقق من سلامتها، منفصلة كلياً عن أي قاعدة تشغيلية.
2. تشغيل أداة preflight للقراءة فقط على تلك النسخة؛ مراجعة كل blocker وwarning ومطابقة النتيجة مع قواعد التفرد والعضويات.
3. بناء control-plane schema/migration runner مُرقّم وقابل للتكرار على PostgreSQL 16 disposable.
4. تنفيذ ETL أحادي الاتجاه تجريبي مع reconciliation دقيقة للأعداد والعلاقات والتجزئات والحالات، مع rollback موثق.
5. مراجعة خدمة المصادقة وسياق الشركة وتدوير مفاتيح التوقيع وإلغاء الجلسات قبل أي ربط بالتطبيق.
6. توسيع العزل إلى جداول الأعمال: composite FKs وRLS، ثم API/services/jobs/reports/files/import/export/cache، مع اختبارات cross-tenant سلبية.
7. لا تفعيل متعدد الشركات ولا نقل قاعدة إنتاج قبل إغلاق جميع بنود بوابة الإطلاق ومراجعتها.

## 5. بوابة إطلاق تعدد الشركات

لا يُفعّل `TENANT_DATA_SCOPING_ENABLED` قبل التحقق من الآتي:

- كل قراءة وكتابة واستعلام CRUD وخدمة وcallback وتقرير ومهمة مجدولة واستيراد/تصدير وملف وتخزين مؤقت مرتبط بسياق الشركة.
- منع الروابط العابرة للشركات على مستوى قاعدة البيانات بمفاتيح مركبة وقيود مناسبة.
- RLS شامل مع تحقق من هوية وسياق شركة موثوق، وفحص إعادة استخدام الاتصالات داخل connection pool.
- اختبار شركتين على الأقل ببيانات ومعرّفات متشابهة، مع إثبات استحالة القراءة أو التعديل بينهما.
- اختبارات HTTP للمصادقة والصلاحيات وIDOR بلا skips.
- ترحيل بيانات تجريبي متكرر، ومطابقة مالية ومخزنية، واختبار rollback وbackup/restore مع الملفات.
- فحص ClamAV فعلي، واختبارات Browser E2E، وأمن الجلسات، واختبارات التزامن والحمل.
- موافقة إصدار موثقة وخطة رجوع قابلة للتنفيذ.

## 6. سياسة التطوير والدمج

- لا إعادة كتابة Flask/JavaScript أو نقل قاعدة البيانات دفعة واحدة دون مبرر وprototype واختبارات.
- كل مرحلة في فرع وPR مستقل؛ لا توسعة PR #1 إلى إعادة هيكلة تشغيلية غير موثقة.
- لا dual-write بين SQLite وPostgreSQL.
- لا تشغيل على بيانات شركات حقيقية قبل اكتمال العزل.
- النسخ الاحتياطية وملفات الشركات أسرار تشغيلية؛ لا تُرفع إلى GitHub العام.
- لا تغيير في الاستضافة أو قواعد البيانات الحية أو مفاتيح التوقيع ضمن أعمال التوثيق أو الاختبار.
- توثيق كل تغيير مع SHA ونتائج CI ونتائج preflight/reconciliation وخطة rollback.

## 7. حدود التكامل مع AI Core

- قد يستهلك ERP خدمات AI Core لتحليل تقارير أو مساعدة المستخدم، عبر API محددة وصلاحيات read-only افتراضياً.
- تظل قواعد العمل المحاسبية والمالية ومخزون الشركات داخل ERP.
- لا يحصل AI Core على وصول مباشر لقواعد البيانات أو الأسرار أو ملفات الشركات.
- يجب عزل السياق والطلبات والتخزين حسب الشركة، وتسجيل التدقيق، وتقديم تعطيل/fallback آمن عند انقطاع النواة.

## 8. ما لا يدخل في هذا المستودع

- AI Chat App وبيانات المحادثات.
- Lumen وسجلات التعلم والتقييم.
- كود AI Core المركزي أو وثائق المعمارية العامة، باستثناء إحالة مختصرة إلى عقد التكامل.

**القرار المعماري:** ERP يحتفظ بخطته المستقلة وبوابات أمانه الخاصة؛ الخطة الرئيسية للمنظومة تضبط التكامل الاختياري، ولا تتجاوز متطلبات عزل بيانات الشركات.


## 9. حالة حماية الفرع

عند إعداد هذا السجل، أظهر GitHub أن الفرع `main` غير محمي (`protected=false`) ولا توجد عليه متطلبات Branch Protection ظاهرة. هذا لا يؤثر في نجاح CI نفسه، لكنه يقلل الضمانات ضد الدفع المباشر أو التغييرات غير المقصودة.

الإجراء الموصى به قبل بدء تغييرات تشغيلية:
- تفعيل طلب Pull Request إلزامي للدمج إلى `main`.
- جعل فحوص Backend وHTTP وPostgreSQL وJavaScript المطلوبة ضمن Status Checks.
- منع Force Push وحذف `main`.
- إبقاء مسارات الترحيل وقواعد البيانات والإنتاج خلف مراجعة منفصلة وبوابات إصدار.

هذا السجل يوثق الحالة ولا يغير إعدادات GitHub. يجب إعادة قراءة Branch Protection قبل تفعيلها للتأكد من أسماء الفحوص الدقيقة وإعداداتها.
