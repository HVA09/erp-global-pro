# ERP Global Pro — Stage25B: عقد ترحيل control plane إلى PostgreSQL

**الحالة:** مواصفة ترحيل؛ لا تنفذ على قاعدة إنتاج  
**قاعدة المصدر الحالية:** SQLite v8  
**وجهة الاختبار:** PostgreSQL 16 مؤقتة / disposable  
**لا نشر ولا اتصال إنتاج في هذه المرحلة**

## 1. جداول المصدر ونطاق النقل الأول

المصدر هو نسخة SQLite v8 متسقة ومستعادة، وليس قاعدة حية تتغير أثناء قراءة ETL.

| جدول SQLite | جدول PostgreSQL المقترح | سياسة النقل |
|---|---|---|
| `roles` | `erp_control.roles` | نقل المفتاح والاسم والوسم والصلاحيات بعد JSON validation وis_system |
| `users` | `erp_control.users` | نقل IDs والبريد والاسم وبصمة scrypt والحالة وآخر دخول ووقت الإنشاء؛ role القديم يصبح legacy metadata |
| `companies` | `erp_control.companies` | نقل الهوية والاسم والقطاع والبلد والعملة والمنطقة الزمنية والحالة |
| `company_memberships` | `erp_control.company_memberships` | نقل IDs وcompany/user/role/status/invited_by/joined_at/created_at مع الحفاظ على unique(company_id,user_id) |

لا ينقل Stage25B بيانات ERP التشغيلية إلى التطبيق، ولا يغير مخطط SQLite. الهدف هو التحقق من سلامة control-plane import على نسخة اختبار فقط. الترحيل النهائي لجميع بيانات ERP يأتي بعد إتمام adapter والمخطط والمفاتيح المركبة وRLS ومسارات الملفات والنسخ والاستعادة.

## 2. Preflight إلزامي قبل أي استيراد

أنشئ تقريرًا غير تعديلي يتضمن:

### users
- العدد الإجمالي.
- تكرار البريد بعد `strip + casefold` وفق دالة canonical واحدة محددة في التطبيق.
- البريد الفارغ أو غير الصالح وفق قواعد المنتج.
- المستخدمون غير النشطين.
- hashes المفقودة أو التي لا تطابق صيغة scrypt المعروفة.
- أي اختلاف في تمثيل البريد بين الجدول والمفهرس/التطبيق.

### roles
- العدد الإجمالي.
- أسماء الأدوار المكررة (يجب أن تكون مستحيلة مع PK، لكن يعاد التحقق).
- `permissions` لكل دور: JSON صالح ومصفوفة نصوص فقط.
- كل دور مستخدم في العضويات أو legacy users.role موجود.
- حفظ permission arrays بعد التطبيع دون تغيير أسماء الصلاحيات أو wildcard patterns.

### companies
- العدد الإجمالي.
- حالات الشركات غير المعروفة.
- الحقول المطلوبة الفارغة.
- قيم العملة/المنطقة الزمنية غير الصالحة.
- عدم إنشاء شركة تلقائيًا أثناء ETL إذا لم توجد في المصدر؛ يجب أن يظهر غيابها كخطأ.

### company_memberships
- العدد الإجمالي.
- عضويات يتيمة إلى user/company/role.
- تكرار (company_id,user_id).
- حالات غير معروفة.
- أعضاء نشطون في شركات غير نشطة أو مستخدمين غير نشطين؛ تُسجل كحالات تستلزم مراجعة ولا تُصحح ضمنيًا.
- عدد العضويات لكل مستخدم، وتطابق كل membership.role مع roles.name.
- مقارنة `users.role` بأدوار العضويات بوصفه legacy consistency report فقط؛ لا يُستخدم لتغيير role membership.

### audit and references
- عدد audit_log المرتبط بالمستخدمين/الشركات، مع احترام إمكانية وجود أحداث نظامية بلا company_id.
- فحص كل FK وتحديد السجلات المرجعية المفقودة.
- عدم حذف أو إسقاط أي مستخدم/شركة/عضوية صامتًا.

**قاعدة:** إذا كان هناك خطأ أو تصادم غير مفهوم، يتوقف الترحيل قبل INSERT النهائي. لا تستخدم `INSERT ... ON CONFLICT DO NOTHING` لإخفاء اختلافات البيانات.

## 3. مواصفة مخطط PostgreSQL

### schema and migration history
- مخطط control مستقل باسم `erp_control`، مع security schema منفصل.
- جدول `schema_migrations(version, name, checksum, applied_at, applied_by)`.
- الترحيل بترتيب واضح، checksum ثابت، قفل ترحيل (advisory lock أو آلية مكافئة)، ومعاملة واحدة لكل migration حيثما أمكن.
- لا تستخدم `executescript`; نفّذ statements صريحة عبر runner يدعم transaction وإظهار المرحلة التي فشلت.
- لا يسمح بتغيير migration مطبقة؛ أضف migration جديدة مع rollback/forward plan.

### companies
- `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`.
- حقول الشركة الحالية، مع CHECK لقيم status.
- FK/قيود صريحة وعدم حذف شركة عليها عضويات أو بيانات.

### users
- `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`.
- `email` للعرض، و`email_normalized` غير فارغ وفريد بعد canonicalization.
- `password_hash` نص يحتفظ حرفيًا بصيغة scrypt.
- `is_active BOOLEAN NOT NULL`.
- `legacy_role` اختياري لأغراض الانتقال والمراجعة فقط، ولا يستخدم للتفويض.
- timestamps من نوع `TIMESTAMPTZ` بعد validation.

### roles
- الحفاظ على `name TEXT PRIMARY KEY` كما هو في SQLite؛ لا حاجة لإضافة role ID مصطنع خلال الترحيل الأول.
- `label TEXT NOT NULL`.
- `permissions JSONB NOT NULL` مع CHECK يتأكد أن القيمة array من strings فقط.
- `is_system BOOLEAN NOT NULL`.
- تبقى `company_memberships.role` مفتاحًا أجنبيًا إلى `roles(name)`.
- لا يمنح operational app role صلاحية تعديل تعريفات الأدوار العامة.
- لا يفترض هذا المخطط وجود company-specific custom roles؛ أضيفت كمطلب منفصل إذا تقرر دعمها.

### company_memberships
- `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`.
- FKs إلى `companies`, `users`, و`roles`.
- `UNIQUE(company_id,user_id)`.
- CHECK للحالات المعروفة.
- فهارس على (user_id,status) و(company_id,status).
- لا تسمح بتعديل role/status من endpoint عام؛ كل mutation تحتاج إجراء تفويض وإلغاء سياق قائم.

### auth challenges and signing keys
- challenge tokens عشوائية عالية الإنتروبيا؛ تخزن بصمتها فقط، مع user_id, purpose, created_at, expires_at, consumed_at, attempts.
- لا يقبل إجراء إنشاء challenge قيمة user_id من العميل. تُنشئه خدمة المصادقة فقط بعد التحقق من scrypt.
- عرض الشركات والتحقق من اختيار الشركة يجريان بإجراءات محدودة تستند إلى challenge.
- key material في schema خاص مملوك لدور `NOLOGIN`، لا يستطيع `erp_app` أو `erp_auth` قراءة مفاتيحه مباشرة.
- key_id/rotation state موثقان؛ لا تسجل أسرار أو signatures في logs.

## 4. ضوابط ETL والاستيراد

1. أخذ نسخة SQLite متسقة باستخدام آلية backup الحالية أو نسخة offline بعد إيقاف الكتابة.
2. حفظ SHA-256 لملف قاعدة المصدر، وmanifest لحزمة الملفات إن وجدت.
3. قراءة المصدر read-only، وإنتاج preflight report قبل لمس PostgreSQL.
4. تحميل البيانات إلى staging tables في قاعدة disposable.
5. canonicalize البريد والصلاحيات والتواريخ عبر دوال deterministic ذات إصدارات معروفة.
6. preserve IDs في كل الجداول وعدم توليد معرفات بديلة.
7. استيراد roles ثم companies ثم users ثم company_memberships بترتيب FK.
8. بعد الاستيراد، إعادة ضبط identity sequences لأكبر ID + 1.
9. إجراء FK checks وunique checks وrow counts ومطابقة checksums لكل جدول.
10. اختبار تحقق scrypt على عينات اصطناعية/نسخ اختبار لا تحتوي أسرارًا في logs.
11. إصدار تقرير مقارنة يشرح كل اختلاف. يمنع حذف أو دمج أي سجل دون mapping معتمد.
12. إسقاط قاعدة الاختبار وإعادة تشغيل العملية من الصفر لإثبات التكرارية وإمكانية إعادة البناء.

## 5. Canonicalization وقواعد التحويل

- البريد: يحافظ على النص الأصلي للعرض؛ canonical value تحسب بدالة واحدة مثل `strip().casefold()` في Python، وتستخدم في جميع المسارات. افحص التصادمات قبل إضافة unique constraint.
- permissions: parse JSON إلى مصفوفة نصوص؛ رفض object أو scalar أو عناصر غير نصية أو JSON غير صالح.
- password_hash: نقل حرفي؛ لا إعادة hashing جماعية ولا طباعة للقيمة.
- booleans: تحويل 0/1 إلى BOOLEAN بعد رفض أي قيمة أخرى.
- timestamps: لا تفترض timezone غير معروف. قيم SQLite المولدة بـ`datetime('now')` UTC؛ أي format آخر يُصنف ويختبر قبل تحويله.
- money: integers minor units دون float.
- النصوص: تحافظ على Unicode؛ تقرير منفصل للقيم التي تحتوي NUL أو bytes غير صالحة.

## 6. Reconciliation — شروط المطابقة

يصدر تقرير machine-readable وملخص بشري لكل جدول، ويتضمن:

- source_count, target_count, missing_ids, extra_ids, duplicate_business_keys.
- عدد السجلات المتطابقة بعد canonicalization.
- SHA-256 canonical row digest حسب ترتيب PK، مع versioned canonical serialization.
- FK violation counts.
- role/permissions mapping.
- memberships لكل user/company وحالات inactive/suspended.
- scrypt verification sample outcome دون كشف hash.
- mismatch report لكل timestamp أو بريد أو حالة.
- لا يعد نجاح row counts وحده كافيًا.

في مرحلة ترحيل ERP الكاملة، تضاف:
- trial balance متوازن لكل شركة.
- P&L وbalance sheet وcash-flow controls.
- inventory quantities and value reconciliation.
- payment/document totals.
- payroll totals.
- attachment object count/size/SHA-256 وbackup/restore checks.

## 7. خطة القطع النهائي — مستقبلية فقط

لا تجرى في Stage25B. عند جاهزية التطبيق بأكمله:

1. إيقاف استقبال الكتابات وتفعيل maintenance mode.
2. إيقاف كل workers والمهام الخلفية والتكاملات التي تكتب.
3. أخذ backup نهائي متسق للـSQLite والملفات.
4. تشغيل preflight وETL النهائي إلى PostgreSQL المرشح.
5. تنفيذ reconciliation كاملة لكل البيانات والملفات.
6. إجراء smoke tests للمصادقة وتبديل الشركة وقراءة/كتابة الأعمال والتقارير والملفات والنسخ.
7. تحويل إعداد DB مرة واحدة بعد موافقة release gate؛ لا dual-write ولا تشغيل active-active.
8. مراقبة الأخطاء والقيود والاتصالات وRLS.
9. الاحتفاظ بنسخة SQLite النهائية read-only. يسمح بالرجوع إلى SQLite فقط قبل قبول أي كتابات جديدة على PostgreSQL؛ بعد بدء الكتابة على PostgreSQL يلزم forward-fix أو إجراء استرداد معتمد، ولا يجوز الرجوع عشوائيًا إلى نسخة قديمة وفقد المعاملات.

## 8. الاختبارات المطلوبة في Stage25B

- ترحيل IDs مع الحفاظ على PKs وFks.
- تطابق counts وunique keys وrow digests.
- تصادم البريد قبل canonicalization وبعدها.
- كل حالة role/membership/status.
- password hash verification دون كشف secrets.
- missing/invalid JSON permissions.
- malformed timestamps and boolean values.
- rerun/idempotency and interrupted migration.
- rollback transaction عند خطأ FK أو uniqueness.
- عدم صلاحية `erp_app` لقراءة control tables/key material.
- لا توجد كتابة إلى SQLite أو PostgreSQL الفعلية أثناء هذه الاختبارات.

## 9. شروط الخروج من Stage25B

- اكتمال preflight على نسخة SQLite مستعادة.
- schema control-plane مرقم ومختبر على PostgreSQL 16 disposable.
- ETL أولي قابل للتكرار مع تقرير reconciliation.
- كل التناقضات في legacy_role والأدوار والعضويات محسومة أو موثقة.
- قرار موثق بشأن company-specific roles.
- مصادقة scrypt وإجراء pre-company challenge مصممان ومختبران.
- لا اتصال تشغيل بين Flask وPostgreSQL بعد.
- لا تغيير لSQLite v8 أو `TENANT_DATA_SCOPING_ENABLED=False`.
