# دليل تشغيل المرفقات والنسخ الاحتياطي — Stage 16

## 1. متغيرات البيئة

```env
ERP_FILE_STORAGE_DIR=backend/instance/files
ERP_FILE_QUOTA_BYTES=262144000
ERP_FILE_UPLOADS_PER_HOUR=30
ERP_CLAMSCAN_BIN=clamscan
ERP_MAINTENANCE_MODE=0
```

يجب أن يبقى `ERP_FILE_STORAGE_DIR` خارج مجلد الواجهة العامة وstatic. استخدم volume خاصًا بصلاحيات نظام ملفات ضيقة. لا تضف مجلد `instance` أو المرفقات إلى Git.

## 2. فحص الملفات

تحتاج عملية الفحص إلى تثبيت ClamAV على خادم التطبيق وتوفير executable اسمه `clamscan` (أو تحديد مساره في `ERP_CLAMSCAN_BIN`). تحديث قاعدة الفيروسات مسؤولية مشغل الخادم.

من مجلد `backend`:

```bash
python manage.py scan-files
python manage.py scan-files --retry-errors
python manage.py check-files
python manage.py audit-file-orphans /secure/reports/file-orphans.json
```

- قبل الفحص وبعده يتحقق التطبيق من الحجم وSHA-256؛ إذا تغيرت bytes فلا يمكن للماسح اعتمادها `clean`.
- يعاد التحقق من الحجم وSHA-256 عند كل تنزيل، وتُحوّل metadata إلى `error` عند اكتشاف اختلاف بعد الفحص.
- لا يعتبر الملف سليمًا ما لم يرجع ClamAV بنتيجة نظيفة وكانت bytes مطابقة للبصمة المسجلة.
- لا يمكن تنزيل `pending` أو `infected` أو `error`.
- الملفات المصابة تُنقل إلى `.quarantine/<company_id>/`. مسارات root وtenant وquarantine التي تستخدم symlinks مرفوضة؛ إذا كان الحجر غير آمن تفشل العملية بشكل مغلق وتظل حالة الملف `error`.
- تقرير الملفات اليتيمة لا يحذف أي شيء؛ راجع التقرير يدويًا قبل أي تنظيف.
- إذا لم يكن ClamAV متوفرًا، تبقى الملفات معلقة وغير قابلة للتنزيل. لا تغير الحالة يدويًا إلى `clean`.

## 3. إدارة المرفقات داخل ERP

من شاشة **المستندات**:

- يظهر قسم المرفقات الخاصة مع الحصة وعدد الملفات.
- الرفع يقبل PDF وPNG وJPG/JPEG وWEBP وTXT وCSV، بحد أقصى 10 MiB للملف.
- الحصة الافتراضية 250 MiB لكل شركة.
- الحد الافتراضي 30 عملية رفع لكل مستخدم/شركة في ساعة.
- الملفات لا تصبح قابلة للتنزيل حتى ينجح فحص ClamAV.
- حذف الملف يتطلب `documents.write`؛ تنزيل/عرض القائمة يتطلب `documents.read`.

## 4. إنشاء نسخة احتياطية شاملة

ينشئ الأمر لقطة SQLite والملفات الخاصة المسجلة مع manifest وبصمات SHA-256:

```bash
cd backend
python manage.py backup-bundle /secure/backups/erp-full-2026-11-13.zip
```

يمكن تشغيل backup أثناء عمل التطبيق؛ إذا تغيرت bytes أو اختفت أثناء تكوين النسخة فسيفشل إنشاء bundle بدل تسليم نسخة جزئية. يجب حفظ الملف في موقع خاص، خارج قاعدة البيانات ومجلد التخزين، وعدم رفعه إلى GitHub أو مشاركته علنًا.

**التشفير:** صيغة ZIP هنا غير مشفرة وغير موقعة رقميًا. احفظ النسخ على وسيط مشفر ومقيد الصلاحيات، ولا ترفعها إلى GitHub أو مخزن عام. بصمة SHA-256 تتحقق من مطابقة bytes للـmanifest وتساعد في كشف التلف العرضي، لكنها لا تمثل توقيعًا موثوقًا للمصدر ولا تمنع مهاجمًا قادرًا على استبدال الأرشيف والـmanifest معًا.

يستخدم الأمر صلاحيات ملفات مقيدة (ملفات DB/ZIP خاصة ومجلدات خاصة) حيث يدعم نظام التشغيل ذلك. راجع صلاحيات مجلد النسخ ومستخدم الخدمة يدويًا بعد النشر.

## 5. استعادة نسخة احتياطية

1. أوقف كل web workers والجدولة والعمليات الخلفية التي قد تكتب إلى ERP.
2. تأكد من أن `ERP_DB_PATH` و`ERP_FILE_STORAGE_DIR` على نظام الملفات نفسه؛ يلزم ذلك لتبديل rollback-safe.
3. خذ نسخة خارجية احتياطية من الحالة الحالية قبل الاستعادة.
4. شغّل الأمر بوضع الصيانة:

```bash
cd backend
ERP_MAINTENANCE_MODE=1 python manage.py restore-bundle /secure/backups/erp-full.zip
```

5. تحقق من ظهور `restored: true`، ثم نفّذ:

```bash
python manage.py check
python manage.py check-files
```

6. تحقق من المرفقات ووحدات الأعمال يدويًا قبل إعادة تشغيل الويب.
7. احتفظ بمجلدات `.pre-restore-<id>` التي أعادها الأمر حتى اكتمال التحقق. لا تحذفها آليًا؛ لا يوجد retention/cleanup لهذه النسخ حتى الآن.

لا تبدأ خادم الويب أثناء الاستعادة. إذا انقطعت الاستعادة وظهر restore journal، سيمنع التطبيق بدء التشغيل. بعد إيقاف كل العمليات، نفّذ:

```bash
cd backend
python manage.py recover-bundle-restore
```

هذا الأمر يعيد قاعدة البيانات ومجلد التخزين السابقين حسب journal. إذا فشلت عملية recovery، أبقِ الخادم متوقفًا واحتفظ بالـjournal ومجلدات pre-restore واطلب مراجعة يدوية؛ لا تحذفها ولا تعدلها يدويًا.

## 6. ترقية Stage 15 إلى Stage 16

عند بدء التطبيق على قاعدة Stage 15، تعمل الترحيلات تلقائيًا إلى SQLite v8. تضيف الترحيلة حالة فحص افتراضية `pending` إلى المرفقات القديمة. يجب تشغيل `scan-files` قبل السماح بتنزيلها. خذ نسخة احتياطية من قاعدة البيانات والملفات قبل أي ترقية على بيئة حقيقية.

## 7. حدود الإصدار

- لم تُختبر عملية ClamAV فعلية في بيئة البناء الحالية؛ اختبارات المرحلة استخدمت executable وهميًا يحاكي نتائج clean/infected.
- لم تُشغّل اختبارات HTTP/Flask أو browser E2E؛ Flask غير مثبت في بيئة البناء.
- اختبارات الملفات تتضمن أيضًا رفض symlink في جذر التخزين ومجلد الشركة ومجلد الحجر؛ لا تستخدم مجلد تخزين مشتركًا قابلًا للكتابة من مستخدمين آخرين.
- اختبارات حزمة النسخ/الاستعادة ترفض symlink وZIP directory entries غير المتوقعة ومسارات DB/storage المتداخلة.
- لم تُنفذ PostgreSQL أو RLS.
- لم تُشغل اختبارات Flask/HTTP أو browser E2E الفعلية في بيئة البناء الحالية.
- إبقاء تعدد الشركات في الإنتاج مغلقًا إلزامي حتى اجتياز بوابات العزل الكاملة.
