# سجل تغييرات ERP Global Pro — Stage 11

**المرحلة:** عزل خدمات المبيعات والمشتريات والمدفوعات (Trade / Payments)
**التاريخ:** 13 نوفمبر 2026
**قاعدة البيانات:** لا تغيير في المخطط؛ بقي `LATEST_VERSION = 6`.
**نطاق العمل:** `backend/erp/services/trade.py` و`backend/erp/api/trade.py` واختبارات العزل.

## 1. التغييرات المنفذة

### خدمات المستندات التجارية
- إضافة محلّل سياق الشركة `_cid()` إلى خدمة التجارة، ويعتمد على `tenancy.current_company_id()`.
- جعل تحميل المستندات (`_fetch`) مقصورًا على المستند التابع للشركة النشطة، مع ربط الشريك والمستودع والمستند الأصلي ضمن الشركة نفسها.
- حصر بنود المستند والمدفوعات وتطبيقات الأرصدة في `get_doc()` حسب `company_id`، مع تقييد joins للحسابات والمنتجات والمستندات المرتبطة بالشركة ذاتها.
- تقييد القوائم والبحث والعدّ وميزانيات العملاء والموردين وكشوف الحسابات وتقارير أعمار الديون حسب الشركة.
- التحقق من ملكية الشريك والمنتج والحساب والمستودع والمستند الأصلي قبل إنشاء مستند أو تعديله.
- إدراج `company_id` من سياق الخادم في `trade_documents` و`trade_document_lines`، وعدم الوثوق بأي قيمة مماثلة يرسلها العميل.
- تقييد تعديل وحذف المسودات بالمستند والشركة، ومنع الوصول إلى معرف مستند تابع لشركة أخرى.

### الترحيل المحاسبي والمخزني والمدفوعات
- تمرير `company_id` إلى خدمات المخزون والمحاسبة والتسلسلات والإعدادات عند ترحيل فاتورة أو إشعار دائن/مدين أو فاتورة مشتريات.
- تقييد احتساب المرتجعات وتكلفة وحدة المستند الأصلي وحركات المخزون حسب الشركة.
- تقييد عمليات إلغاء المستند وعكس قيده وحركاته والتحقق من الفترة المالية ضمن الشركة النشطة.
- تقييد إعادة احتساب المدفوعات، وإنشاء المدفوعات وإلغائها، وتطبيق الأرصدة الدائنة وإلغائها.
- ربط المدفوعات والمستندات والشركاء والحسابات في القوائم وكشوف الحسابات ضمن `company_id` نفسه.
- إنشاء عميل POS الافتراضي لكل شركة وتمرير سياق الشركة عبر عملية إتمام البيع والتحصيل.

### واجهات API
- تقييد قائمة حسابات الدفع في `/api/payment-accounts` إلى الحسابات النقدية/البنكية التابعة للشركة النشطة الموثقة في `g.company`.
- بقية نقاط التجارة تستدعي الخدمات بعد تحميل هوية المستخدم والسياق النشط من JWT والعضوية؛ لم تُضف معلمة شركة قابلة للتحكم من body أو header.

## 2. الاختبارات

أضيف `backend/tests/test_tenant_stage11_trade_scope.py` وفيه 14 اختبارًا مركّزًا يغطي:
- منع قراءة مستند شركة أخرى بالمعرف المباشر.
- منع تسرب البنود والمدفوعات وتطبيقات الائتمان التابعة لشركة أخرى.
- قوائم المستندات والمدفوعات وكشف الحساب وأعمار الديون ضمن الشركة النشطة.
- رفض الشريك أو المنتج أو الحساب المرجعي التابع لشركة أخرى.
- ختم `company_id` من جهة الخادم ورفض company context المخالف.
- رفض الوصول إلى معرف دفع أو تطبيق ائتمان عابر للشركات.
- تمرير الشركة نفسها إلى عملية الترحيل والقيد المحاسبي والمدفوعات.
- عزل عميل POS الافتراضي لكل شركة.

**نتيجة مجموعة اختبارات tenancy الكاملة:** 70/70 ناجحة، بما فيها اختبارات المراحل السابقة حتى Stage 11.
**Python:** `compileall` ناجح.
**JavaScript:** 19/19 ملفًا اجتاز `node --check`.
**فحص AST:** ملفات خدمة التجارة وواجهة التجارة سليمة نحويًا.

اختبارات Stage 11 تحمل كود خدمة التجارة الفعلي وتنفّذه على SQLite مع طبقة بديلة مخصصة لاختبار Flask/DB والخدمات التابعة؛ لذلك هي اختبارات وحدة/خدمة مركزة وليست اختبار HTTP أو E2E.

## 3. ما لم يتم اختباره أو تنفيذه

- Flask غير مثبت في بيئة التحقق؛ لم تُشغّل اختبارات Flask/HTTP الكاملة، ولا اختبارات المتصفح أو E2E.
- لم يتم تنفيذ PostgreSQL أو Row-Level Security.
- لم تُجر اختبارات أداء أو معاملات متزامنة لعمليات الترحيل والتحصيل.
- لم يُفحص ملف قاعدة بيانات إنتاج أو تُجر تجربة ترحيل على نسخة حقيقية.
- خدمات HR/Payroll/Manufacturing لم تُعتمد ضمن هذا التسليم؛ هي المرحلة التالية منفصلة.
- لم يُفعّل `TENANT_DATA_SCOPING_ENABLED`، ولم يُنشر النظام متعدد الشركات.

## 4. قرار الإصدار

Stage 11 نقطة تطوير قابلة للاسترجاع، وليست إصدارًا جاهزًا لتشغيل عدة شركات. يجب أن يبقى حاجز التشغيل متعدد الشركات مغلقًا إلى أن تكتمل بقية الخدمات وواجهات API والتقارير والملفات والاستيراد/التصدير والمهام الخلفية، ثم اختبارات HTTP فعلية لشركتين وPostgreSQL/RLS ومراجعة Release Gate.
