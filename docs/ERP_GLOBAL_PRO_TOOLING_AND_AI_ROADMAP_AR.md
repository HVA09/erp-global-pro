# خطة أدوات التطوير والذكاء الاصطناعي — ERP Global Pro

> الحالة: وثيقة تخطيط واعتماد اتجاهات، وليست دليلاً على تثبيت الأدوات أو ربط الحسابات أو تفعيل ميزات في الإنتاج.
> النطاق: المراحل 26–34، تطوير مرحلي فوق البنية الحالية.

## 1. القرارات المعتمدة

| البند | القرار |
|---|---|
| الميزانية | Free-first: تفضيل الأدوات المجانية ومفتوحة المصدر، ومراجعة حدود الخطط المجانية قبل الاعتماد |
| الاستضافة | Hybrid: تطوير واختبار محليان مع خدمات سحابية عند الحاجة |
| CI/CD | Flexible: GitHub Actions حالياً، مع إبقاء أوامر البناء والاختبار مستقلة قدر الإمكان عن المزود |
| بنية التطبيق | الاحتفاظ بـ Flask وواجهة JavaScript الحالية ووحدات ERP؛ لا إعادة بناء شاملة |
| قاعدة الإنتاج المستهدفة | PostgreSQL |
| تعدد الشركات | Multi-tenant مع عزل إلزامي ومثبت قبل التفعيل |
| تفعيل العزل | يظل TENANT_DATA_SCOPING_ENABLED=False حتى اجتياز بوابات القبول وإثبات العزل |
| دمج AI | خدمة مستقلة واختيارية لكل Tenant، وليست جزءاً من منطق المحاسبة أو المخزون الأساسي |

## 2. مبادئ اختيار الأدوات

1. Free-first وليس Free-only: لا نفترض أن الخطط المجانية دائمة أو كافية للإنتاج؛ نراجع الحدود والتكلفة والخصوصية قبل الاستخدام.
2. لا نضيف أداة قبل وجود حاجة مرتبطة بمرحلة ومعيار قبول واضح.
3. لا نرفع قواعد بيانات حقيقية أو أسراراً أو ملفات .env أو نسخاً احتياطية إلى GitHub أو إلى مزودي AI.
4. كل خدمة سحابية تخضع لتقييم موقع تخزين البيانات، وسياسة الاحتفاظ، والتحكم بالوصول، والتكلفة.
5. لا تُفعّل أدوات AI أو Multi-Tenant في الإنتاج لمجرد نجاح نموذج أولي.
6. لا يتم نشر أي تغيير على main مباشرة؛ التغييرات عبر فرع وPull Request ومراجعة.

## 3. مجموعة الأدوات المقترحة

### 3.1 تطوير وجودة الكود والاختبار

| المجال | الأداة | الاستخدام المخطط |
|---|---|---|
| مستودع ومراجعة | GitHub | Issues وPull Requests ومراجعة التغييرات |
| CI/CD | GitHub Actions | تشغيل الفحوصات والاختبارات وبناء الإصدارات |
| Python lint/format | Ruff | فحص وتنسيق كود Python |
| اختبارات خلفية | pytest | اختبارات الوحدات والتكامل |
| اختبارات الواجهة | Playwright | سيناريوهات E2E للواجهات |
| اختبار API | Postman أو Schemathesis | اختبارات API؛ يختار أحدهما حسب وجود OpenAPI والحاجة |
| كشف الأسرار | Gitleaks | منع تسرب المفاتيح والبيانات الحساسة |
| تحديث الاعتماديات | Renovate | Pull Requests لتحديث المكتبات |
| جودة إضافية | SonarQube Cloud | خيار لاحق إذا كانت الخطة المجانية وشروطها مناسبة |

### 3.2 قاعدة البيانات والبنية التحتية

| المجال | الأداة | الاستخدام المخطط |
|---|---|---|
| قاعدة البيانات | PostgreSQL | قاعدة البيانات المستهدفة للإنتاج |
| بيئة قابلة للتكرار | Docker / Docker Compose | تشغيل خدمات التطوير والاختبار |
| إدارة DB | DBeaver Community | استكشاف قواعد التطوير والاختبار |
| PostgreSQL سحابي | Neon (اختياري) | بيئة تطوير/اختبار سحابية؛ لا اعتماد إنتاجي قبل تقييم الخصوصية والتكلفة |
| تخزين كائنات | MinIO (عند الحاجة) | تخزين ملفات منفصل بواجهة S3-compatible |

### 3.3 الأمن والأداء والمراقبة

| المجال | الأداة | الاستخدام المخطط |
|---|---|---|
| تحليل أمني ثابت | Semgrep | فحص أنماط الكود الخطرة |
| فحص الاعتماديات والصور | Trivy | كشف الثغرات في الحزم وصور الحاويات |
| فحص تطبيق الويب | OWASP ZAP | اختبار أمني في بيئة اختبار مصرح بها |
| اختبارات الحمل | Locust | قياس الأداء والتحمل |
| المقاييس | Prometheus | جمع المقاييس |
| لوحات المراقبة | Grafana | عرض المقاييس والتنبيهات |
| تتبع الأخطاء | Sentry (اختياري) | تتبع أخطاء التشغيل بعد تقييم سياسة البيانات |
| الرصد الموزع | OpenTelemetry | توحيد traces/metrics/logs عند الحاجة |

### 3.4 الذكاء الاصطناعي المساعد للتطوير

| الأداة | الاستخدام | قرار الدمج |
|---|---|---|
| GitHub Copilot | مساعدة المطور في فهم الكود والاختبارات والاقتراحات | اختياري؛ لا يملك صلاحية دمج أو نشر تلقائي |
| Gemini Code Assist | بديل للمقارنة والتحقق من جودة الاقتراحات | اختياري |
| نماذج محلية عبر Ollama | تجارب محلية تقلل إرسال الشيفرة إلى مزود خارجي | تجربة في بيئة التطوير بعد تقييم موارد الجهاز |
| مراجعة بشرية | التحقق من كل اقتراح مولّد | إلزامية |

لا تُعامل مخرجات مساعد البرمجة كدليل صحة. كل تغيير مقترح يمر بالاختبارات والمراجعة المعتادة.

### 3.5 الذكاء الاصطناعي داخل ERP

| المكوّن | الدور المخطط | التوقيت |
|---|---|---|
| Dify | تصميم AI workflows وRAG ومساعدات المعرفة | نموذج أولي بعد استقرار الأساس |
| LiteLLM | بوابة موحدة لمزودي النماذج وتوجيه الطلبات | عند بدء دعم أكثر من نموذج/مزود |
| Ollama | تشغيل نماذج محلية عند توفر موارد مناسبة | خيار خاص بالشركات التي تحتاج معالجة محلية |
| Langfuse | تتبع الاستدعاءات والتكلفة والجودة والتقييم | قبل إطلاق AI للمستخدمين |
| قاعدة معرفة RAG | البحث في وثائق الشركة ودليل ERP | بعد تصميم صلاحيات الوثائق وعزل Tenant |

هذه مكونات مقترحة وليست قرارات لشراء خدمة أو ربط حساب أو تشغيل نموذج بعينه. يجب إعادة تقييم نشاط المشاريع، الرخص، الأسعار، وسياسات البيانات وقت التنفيذ.

## 4. خريطة دمج الأدوات حسب المراحل

### Stage 26 — Full Codebase Audit
- جرد البنية والاعتماديات والاختبارات الحالية.
- مراجعة GitHub Actions الحالية قبل تغييرها.
- استخدام pytest لتحديد خط أساس الاختبارات.
- تجربة Ruff على نطاق قياس أولاً، ثم اعتماد قواعد متوافقة مع الكود.
- فحص الأسرار باستخدام Gitleaks.
- استخدام مساعد AI اختيارياً للفهم والشرح، مع مراجعة بشرية لكل استنتاج.
- المخرجات: تقرير تدقيق، مخاطر، خريطة اعتماديات، وخط أساس قابل للتكرار.
- لا تعديل معماري قبل توثيق نتائج التدقيق.

### Stage 27 — Multi-Tenant Architecture
- تصميم Tenant/Company/User وعلاقات الملكية والصلاحيات.
- تحديد tenant context موثوق لا يُقبل من مدخلات المستخدم دون تحقق.
- إعداد مصفوفة ملكية البيانات ومسارات API والخدمات والملفات والمهام.
- كتابة اختبارات سلبية تثبت منع الوصول بين المستأجرين.
- مراجعة تصميم RLS وسياسات PostgreSQL.
- عدم تفعيل TENANT_DATA_SCOPING_ENABLED قبل اجتياز معايير العزل.

### Stage 28 — PostgreSQL Foundation
- إعداد PostgreSQL محلياً عبر Docker Compose.
- تشغيل اختبارات PostgreSQL في GitHub Actions.
- استخدام DBeaver لإدارة قواعد التطوير والاختبار.
- تقييم Neon كبيئة سحابية غير إنتاجية عند الحاجة فقط.
- توثيق migrations والاتصال والأسرار والنسخ الاحتياطي.
- لا نقل إنتاجي في هذه المرحلة.

### Stage 29 — SQLite to PostgreSQL Migration / ETL
- بناء ETL قابل لإعادة التشغيل مع سجل أخطاء.
- التحقق من أعداد السجلات والعلاقات والقيود والقيم.
- استخدام pytest واختبارات مطابقة مستقلة.
- تشغيل اختبارات الهجرة على بيانات اصطناعية في CI.
- يمكن استخدام AI لشرح أخطاء ETL أو اقتراح mapping فقط؛ لا يُعتمد على AI لإقرار صحة البيانات.
- إعداد rollback موثق ومجرب.

### Stage 30 — Multi-Tenant Integration
- تمرير tenant context عبر API والخدمات والملفات والمهام الخلفية.
- اختبار عزل البيانات والملفات والمهام.
- مراجعة RLS كطبقة دفاع إضافية، لا كبديل عن فحص التطبيق.
- تقييم MinIO فقط إذا تطلب تصميم الملفات فصلاً أو تخزيناً كائنيّاً.
- إبقاء ميزات AI منفصلة عن مسارات البيانات الأساسية.

### Stage 31 — ERP Module Integration and Validation
- pytest لاختبارات الخدمات وAPI.
- Playwright لسيناريوهات المستخدم الأساسية في الوحدات الموجودة.
- اختبار صلاحيات الأدوار والشركات.
- نموذج أولي محدود لمساعد ERP للقراءة فقط، بعد اكتمال ضوابط tenant والauthorization.
- يمنع تنفيذ قيود مالية أو تعديل مخزون عبر النموذج مباشرة.

### Stage 32 — General-Market Localization
- اختبارات اللغات وRTL/LTR والعملات والدقة العشرية والمناطق الزمنية والضرائب.
- يمكن تقييم AI للترجمة الأولية فقط مع مراجعة بشرية ومصطلحات موحدة.
- يجب عدم استخدام النموذج لتحديد التزامات ضريبية أو قانونية دون قواعد معتمدة ومراجعة مختص.

### Stage 33 — Security, E2E, Load, Backup/Restore
- Semgrep وGitleaks وTrivy.
- OWASP ZAP على بيئة اختبار مصرح بها.
- Playwright E2E وLocust load tests.
- اختبار النسخ الاحتياطي والاستعادة فعلياً.
- عند تجربة AI: تقييم prompt injection وتسريب البيانات والعزل بين Tenants ودقة الاسترجاع وتكلفة الطلب وزمن الاستجابة.
- إضافة Langfuse أو Sentry فقط بعد مراجعة البيانات التي قد تُسجل أو تُرسل خارجياً.

### Stage 34 — Production Deployment and Phased Rollout
- GitHub Actions مع بيئات منفصلة للتطوير والاختبار وStaging وProduction.
- موافقة بشرية قبل النشر الإنتاجي.
- نشر تدريجي مع خطة rollback.
- Prometheus/Grafana ومراقبة الأخطاء والتنبيهات.
- تفعيل ميزات AI تدريجياً وبشكل اختياري لكل Tenant بعد موافقة الشركة وسياسة بيانات واضحة.
- لا تشغيل افتراضي لنموذج سحابي على بيانات العملاء دون موافقة وتقييم خصوصية وتكلفة.

## 5. المعمارية المستهدفة لخدمة AI داخل ERP

ERP Flask Application
  -> AI Gateway (service boundary)
  -> Authentication
  -> Tenant Context + Authorization
  -> Data minimization / redaction
  -> Retrieval layer (tenant-scoped RAG)
  -> Model Router (LiteLLM when needed)
       -> Approved cloud model providers
       -> Local models via Ollama
  -> Observability / evaluation (Langfuse when approved)

### ضوابط إلزامية
1. كل طلب AI مرتبط بهوية المستخدم وTenant موثّق من الخادم.
2. لا يُسمح للنموذج بتحديد Tenant أو تجاوز صلاحيات المستخدم.
3. استرجاع RAG يجب أن يطبق عزل Tenant قبل إرسال السياق إلى النموذج.
4. لا ترسل أسراراً أو بيانات شخصية أو مستندات حساسة إلا وفق سياسة معتمدة وموافقة مناسبة.
5. أدوات AI لا تنفذ SQL حرّاً ولا تكتب مباشرة إلى قاعدة البيانات.
6. عمليات الكتابة الحساسة تمر عبر خدمات ERP ذات الصلاحيات والتدقيق وموافقة المستخدم.
7. إجابات الأرقام والتقارير تستند إلى استعلامات وخدمات موثوقة مع إظهار المصدر والفترة.
8. يجب توفير تعطيل AI لكل Tenant، وتحديد مزود/نموذج وسياسة احتفاظ عند السماح به.
9. تسجيل prompts/responses قد يحتوي بيانات حساسة؛ يكون التسجيل مع تقليل البيانات وإخفاء الحقول وتحديد مدة الاحتفاظ.
10. يجب توفير حدود استخدام ومراقبة تكلفة ومعدل الطلبات وآلية إيقاف عند تجاوز الحدود.

## 6. مسار CI/CD المقترح

Pull Request
  -> Ruff + Gitleaks
  -> pytest
  -> PostgreSQL integration tests
  -> Semgrep / dependency checks
  -> Playwright E2E (when configured)
  -> Merge gate
  -> Build artifact
  -> Deploy to Staging
  -> Smoke tests
  -> Manual production approval
  -> Phased rollout + monitoring

- لا تُضاف أدوات إلى CI دفعة واحدة؛ تُفعّل تدريجياً بعد قياس زمن التشغيل ومعدل الإيجابيات الكاذبة.
- تبقى أوامر الفحص والاختبار قابلة للتشغيل محلياً قدر الإمكان.
- لا يعتمد نجاح CI وحده على إثبات أمن النظام أو عزل المستأجرين.

## 7. بوابات القبول

| البوابة | شرط القبول |
|---|---|
| جودة الكود | نتائج Ruff واضحة ومراجعة الاستثناءات |
| الاختبارات | اختبارات الخلفية والتكامل والواجهة المطلوبة ناجحة |
| العزل | اختبارات سلبية تثبت عدم عبور Tenant boundaries في API/DB/files/jobs |
| الهجرة | مطابقة البيانات والقيود والعلاقات مع rollback مجرب |
| الأمن | لا أسرار مكشوفة ولا ثغرات حرجة غير معالجة قبل الإنتاج |
| الاستعادة | نجاح استعادة نسخة احتياطية في بيئة منفصلة |
| AI privacy | لا وصول عابر للمستأجرين، وتقليل بيانات، وسياسة احتفاظ وموافقة |
| AI quality | تقييم موثق للدقة والاسترجاع والهلوسة والحقن والتكلفة وزمن الاستجابة |
| الإنتاج | Staging ناجح، وموافقة نشر، ومراقبة وخطة تراجع |

## 8. ما لا يدخل في التنفيذ الآن

- لا إعادة بناء شاملة للتطبيق.
- لا نشر مباشر إلى main.
- لا تفعيل Multi-Tenant قبل إثبات العزل.
- لا تشغيل AI على بيانات العملاء قبل مراجعة الخصوصية والصلاحيات.
- لا شراء اشتراكات أو إنشاء حسابات خارجية تلقائياً.
- لا إدخال Kubernetes أو Jenkins في الوقت الحالي دون حاجة تشغيلية مثبتة.
- لا اعتبار أي أداة مذكورة هنا مثبتة أو مفعّلة؛ هذه قائمة تخطيط.

## 9. تسلسل التنفيذ المعتمد

1. استكمال Stage 26 وتوثيق الوضع الفعلي.
2. اعتماد أدوات الجودة والأسرار واختبارها في فرع منفصل.
3. تصميم Multi-Tenant واختبار العزل.
4. تجهيز PostgreSQL وبيئات الاختبار.
5. تنفيذ ETL والتحقق من البيانات.
6. دمج Tenant context في كامل التطبيق.
7. توسيع اختبارات وحدات ERP وE2E.
8. استكمال التوطين.
9. تنفيذ بوابات الأمن والأداء والنسخ والاستعادة.
10. نشر تدريجي، ثم إطلاق AI اختيارياً بعد اجتياز مراجعاته.

**ملاحظة حالة المستودع:** هذه الوثيقة تضيف قرارات التخطيط والأدوات المقترحة فقط. لا تعني أن الأدوات ثُبّتت أو أن خدمات خارجية رُبطت أو أن إعدادات الإنتاج تغيرت. يجب التحقق من الحالة الفعلية لكل أداة في المرحلة التي يجيء دورها.
